- **Attacker dies mid-swing (drain-on-death):** the server applies a normal attack's HP at swing *start* (`Attack_START` → `Apply_DAMAGE`), while the client only presents it at the attacker's *hit frame*. If the player kills a monster before its swing reaches that frame, `Dead()` → `SetCMD_DIE()` interrupts the animation and the monster's already-applied `DamageEvent` orphans in the avatar's `m_CombatDamageQueue` forever. A lingering orphan keeps `has_pending_damage()` true, which gates off **both** reconciliation paths (`DeferCombatHPDriftIfIdle` and the checkpoint fold in `ApplyPresentedCombatDamage`), so the bars stay desynced (client HP > server HP) until the next unrelated hit/`UpdateStats`. `CObjCHAR::Dead()` therefore calls `g_pAVATAR->DrainQueuedCombatDamageFromAttacker(this)`: it discards every event the dying attacker queued on the avatar, lowers authoritative HP via `SetAuthoritativeHPFromDamageEvent` (which only ever lowers, so out-of-order drains are safe), and stages the lost HP as drift so the *next* presented hit silently folds it in (no phantom digit). A lethal orphan on the avatar is a **mutual death**: the attacker that just killed us is being interrupted into its own death motion this very frame and will never reach a hit frame, so no future incoming hit can fold our death in. The drain therefore both `MarkPendingAuthoritativeDeath` **and** `PresentPendingAuthoritativeDeath(pAtkOBJ, ...)` immediately — we already hold the authoritative lethal event and the killer object, so the avatar drops on the same frame as the kill (no freeze, no waiting on a server death packet). This is safe even though it runs inside the dying monster's `Dead()`: the avatar's own `Dead()` skips the drain re-entry via its `this != g_pAVATAR` guard. The `Proc()` backstop (above) still covers the case where this immediate present is somehow not reached. This is avatar-centric on purpose — each client reconciles its own bar; remote bars stay server-reconciled via `UpdateStats`. It is **not** a revival of timeout/missed-hit recovery: it only honors a *real* server event whose presentation animation was destroyed, mirroring the existing `DiscardQueuedCombatDamageFromAttacker` use for bullets that fail to spawn / projectile timeouts. `Dead()` is the single visual-death chokepoint (the `m_bDead = true` flags in `recvpacket.cpp` are pre-death markers; actual death is presented through `Dead()`), so one hook covers all kill paths.
- **No client damage math:** live client combat must not call `CCal::Get_DAMAGE()` or `CCal::Get_SkillDAMAGE()`. Those APIs are server-only for live combat; client usage belongs only in explicit offline/test paths.
- **A stranded orphan disables reconciliation permanently — the sweep is what makes the system self-healing.** Drain-on-death only covers the attacker that *dies*. Every other cancellation path (`Hitted()`, `CancelInterruptedCombatSwingPresentation()`, `DiscardQueuedCombatDamageEvent()`) also needs the attacker object to still exist and to still be tracking that exact `event_id`, and three ordinary situations break both assumptions: the attacker walks out of your sectors (`gsv_SUB_OBJECT` → `CObjectMANAGER::Del_Object`), the zone changes (`CObjectMANAGER::Clear`), or it had **two swings in flight** and only the newest was ever recorded in `m_dwPendingCombatSwingEventId` (`StartConfirmedCombatSwing` overwrites the id without discarding the previous one; the `Proc()` swing sweep then cancels only the tracked one). Because `has_pending_damage()` gates **both** reconciliation paths, one such entry stops HP convergence for that character *for the rest of its life* — every later hit moves the bar by its own digit alone and the drift only accumulates. This is why the drain-on-death unit tests can all pass while the feature looks broken in a real session: the mechanism is correct, it just never runs again after the first poisoning. Three things close it: (1) `Del_Object` drains the departing character's events off the avatar first — also **before** the client object slot can be recycled, since `attacker_id` is a client index and a reused slot would otherwise hand the stale event to whatever spawns next; (2) `Clear()` drops the avatar's queue wholesale on zone change (the server re-states HP at `JOIN_ZONE`, so a checkpoint from the zone you are leaving has no authority in the one you are entering); (3) `CObjCHAR::Proc()` runs a timed **orphaned-damage sweep** (`CombatPresentationQueue::pop_stale_orphan`) as the generic safety net for anything else. The sweep resolves silently — `SetAuthoritativeHPFromDamageEvent` + `DeferCombatHPDriftIfIdle`, **no digit, no hit effect** — because the damage was never presented and inventing it late is a phantom hit. Grace is `kOrphanedDamageGraceMs` (3000 ms, comfortably past any hit frame incl. castle gear's 0.70–1.17 s) with a `kOrphanedDamageHardCapMs` (8000 ms) hard cap so an attacker that swings forever at *someone else* cannot pin an event in your queue. **Lethal events are excluded on purpose** — `pop_stale_lethal` and the pending-death backstop present a *death* for those, and folding one silently would strand the player alive-client / dead-server. Projectile events are held to the hard cap regardless of attacker state: a bullet's timing belongs to the bullet, and a skill projectile arrives as a FlatBuffer `DamageEvent` that never records a pending swing to check against.
  - **The commonest stranding source turned out to be your own death.** Validated log: the avatar dies, its summons despawn mid-swing, and every event those summons had queued on their targets is orphaned at once — nothing drains them, because the drain hook is on the *attacker's* `Dead()` and a despawned summon never presents one. Before the sweep those monsters' bars never reconciled again for the rest of their lives. The sweep catches them at the 3 s grace (`orphaned damage swept … age 3001`). Any death with pets out hits this, which is why the drift reproduced so easily.
  - **Client-synthesized event ids must come from `Rose::Combat::kClientSyntheticEventIdBase`** (`0x80000000`). The four legacy `GSV_DAMAGE` / `GSV_DAMAGE_OF_SKILL` paths mint their own ids because those packets carry none, and they share one per-defender queue with the server's `g_nextCombatEventId`, which starts at 1. `event_id` is the key for `push()` dedupe, `discard_event()`, `has_event()` and `ClearPendingCombatSwingPresentation()`, so an overlapping id **silently drops** a hit on push (no digit, HP checkpoint lost) or discards the wrong event out from under a live swing. Two of the four counters still started at 1 — observed live with server ids at 1..330 and legacy skill ids at 1..10 in the same five minutes. The old 1e6 offsets only deferred it: a busy zone's event rate walks the server into those bands within days of uptime. Setting the high bit is what actually separates the spaces.

- **Death:** death is explicit if `event.lethal`, `event.hp_after <= DEAD_HP`, or pending authoritative death is folded into an incoming hit. For the local avatar, `Reconcile_HP(DEAD_HP)` marks `m_bPendingAuthoritativeDeath` instead of showing synthetic huge damage. While pending-dead, avatar/cart outgoing hit frames present MISS/no damage unless the target event is also lethal; mutual death kills the avatar immediately after the monster's normal lethal presentation. **The fold stands down while the killing blow itself is still queued** (`has_lethal_pending()` on the avatar queue, checked in `ApplyPresentedCombatDamage` after the current event was popped): in a two-swing backlog the earlier, non-lethal swing presents as an ordinary hit and the lethal event presents the death at its own hit frame with its own digit. Before 2026-09-14 the earlier swing became the death (Terrasaurus King: 477 digit, death from a visible 843, the real 619 never shown). The stale-lethal fallback and the Proc() backstop still cover a lethal event whose consumer never fires. Log: `pending death left to queued lethal event`. An avatar/cart hit frame with **no event at all** while pending-dead also presents a bare MISS digit (`Hitted()` NoEvent branch, `ShouldSuppressOutgoingDamageForPendingDeath`): the server committed our death before sending it and every swing it ran was sent earlier on the same socket, so an event-less hit frame after that is a swing the server never ran — the same argument as the committed-dead-attacker phantom-swing rule, mirrored. Digit only, no `ClearStateByHitted()`. Added 2026-09-14 because the death now waits for the killer's impact and the player otherwise sees a couple of seconds of visibly connecting with nothing shown.
- **A lethal legacy skill payload arms pending death at receive (2026-09-14).** `GSV_DAMAGE_OF_SKILL` for a non-projectile skill parks its payload in the *caster's* `m_EffectedSkillList` until that caster's action frame (Terrasaurus King's Charge: 2 s), and pending death used to be armed only when the payload was converted into a queued event there. The server had already committed our death, so in the gap every avatar hit frame found no event and `Hitted()`'s NoEvent branch stayed silent — the "phantom hits" the pending-dead MISS digit exists to replace (`queued presentation miss … queue 0` twice before `skill damage queued`). `Recv_gsv_DAMAGE_OF_SKILL` now calls `MarkPendingLethalSkillPayload(caster)` when the deferred payload's `m_iHP_AFTER <= DEAD_HP` and the target is the avatar: pending death is flagged at once, and the caster + receive tick are remembered so `HasLiveLethalSkillPayloadPending()` (caster alive, under the 6 s cap) defers the backstop and stands the backlog fold down exactly like a queued lethal event does. `PushCombatDamageEvent` clears it when the payload becomes a queued lethal event from that caster; `ClearPendingAuthoritativeDeath` clears it with the flag. Log: `lethal skill payload pending`.
- **Pending-death backstop (never strand the avatar):** the pending-death mechanism normally relies on a *future incoming hit* to present the death. Two paths can leave the avatar flagged pending-dead with no incoming hit ever arriving: (1) the avatar kills its **only/last** attacker mid-swing (handled instantly — see drain-on-death below), and (2) a **no-attacker server kill** — DoT, fall damage, or an attacker that despawned/went out of range — that arrives via `Reconcile_HP(DEAD_HP)`. Without a safety net the player is alive-client / dead-server and frozen (server rejects input, nothing presents). `CObjCHAR::Proc()` therefore runs a backstop: if the avatar is `m_bPendingAuthoritativeDeath` and still alive client-side for longer than `kPendingAuthoritativeDeathTimeoutMs` (1500 ms), it forces `PresentPendingAuthoritativeDeath(NULL, "pending death timeout")`. `m_dwPendingAuthoritativeDeathTime` is stamped **only on the rising edge** in `MarkPendingAuthoritativeDeath` — the server can re-assert `hp=0` every frame, and re-stamping each call would push the timeout out forever so it never fires. `NULL` attacker is safe: the avatar's AI index is 0 (`AI_Dead` early-returns) and the lethal branch of `ApplyPresentedCombatFeedback` guards every `pAtkOBJ` deref. The timeout is intentionally short insurance, not the primary path — Layer-1 mutual-death-on-kill handles the common case with no delay, so the backstop should rarely fire. It is **not** a revival of timeout/missed-hit damage recovery: it only presents a death the server already committed.
  - **The timer defers behind a live lethal presentation (2026-09-14).** `PushCombatDamageEvent` arms the flag for *every* lethal deferred event on the avatar, and those have a real consumer coming — the killer's hit frame or the bullet impact. The flat 1.5 s timer raced them and won: against a ranged monster every shot landed **~2 s** after its `CombatSwing` was received (wind-up + flight; three consecutive non-lethal shots measured it), so the lethal one presented as `pending death timeout` with `attacker 0` **before the arrow was fired** — and the now-dead avatar made the client monster drop its attack (no-target branch of `ProcCMD_ATTACK` → `SetCMD_STOP`), so the shot never appeared at all. Log signature: `death correction deferred (lethal event queued)` → `presented (pending death timeout)` → `swing motion cancelled … state 0x0 command 0` for that event, with no `queued presentation pop` for it. Melee kills hit the same race whenever the hit frame is past 1.5 s (23% of swings measure ≥ 2 s). The backstop `if` therefore also requires `!m_CombatDamageQueue.has_live_lethal_pending(now, kStaleLethalSwingHardCapMs, DEAD_HP, fnPresentationStillLive)` — the same liveness predicate the orphaned-damage sweep uses, hoisted above the backstop, and the same 6 s hard cap as the spectator fallback. Timeline for a lethal event now: presented by the impact / hit frame (normal path); if the motion is replaced before the bullet spawns, the 3 s swing sweep → `DiscardQueuedCombatDamageEvent` presents the death itself; if the attacker vanishes the event leaves the queue and the timer fires at once; 6 s hard cap regardless. A pending death with **nothing queued** (DoT / fall via `Reconcile_HP`) is exactly the old 1.5 s. Cost: the window where the avatar's own outgoing hits show MISS grows from ≤ 1.5 s to "until impact". Nothing server-side interrupts the client monster meanwhile — after a kill the server's `ProcCMD_ATTACK` goes to `CMD_STOP` with **no** `Send_gsv_STOP`.
- **Spectator stale-death fallback:** remote/non-avatar defenders can also be left visually alive if this client receives a lethal `CombatSwing`/legacy melee death, queues it for the killer's hit frame, but the local representation of that killer never reaches the consumer frame (interrupted animation, command mismatch, already-past frame, missing attacker state). `PushCombatDamageEvent()` pre-marks non-avatar lethal defenders with `m_bDead = true`, and `CObjCHAR::Proc()` pops stale lethal `MeleeHitFrame` events after `kPendingAuthoritativeDeathTimeoutMs` (1500 ms) via `CombatPresentationQueue::pop_stale_lethal()`, then runs normal `ApplyPresentedCombatDamage()`/`Dead()` with the original final-hit digit. `MeleeHitFrame` deaths get the 1.5 s grace plus the live-swing deferral below; `ProjectileImpact` deaths wait for their bullet/skill impact and only ever pop at the 6 s hard cap (2026-09-23 — before that they were excluded outright, and a lethal projectile event whose bullet never presented and whose attacker left the client's sectors was stranded forever: `Del_Object` drains only events queued on the avatar, the orphan sweep excludes lethals, and the server never broadcasts a damage-killed mob's removal, so the monster stayed visually alive and unclickable for the rest of the session — one of the two mechanisms behind the "monsters dead server-side" tester report). **Live-swing deferral:** slow attack motions — cart / castle gear weapons, low attack speed — put the killer's hit frame legitimately later than the 1.5 s grace, and popping early killed one-shot targets mid-swing (stone-hammer battle cart was the repro). The `Proc()` call therefore passes a `swing_still_pending` predicate: while the event's attacker is alive, still in `CMD_ATTACK`, and still holds that exact `event_id` as its pending confirmed swing (for a cart/castle gear attacker the pending swing lives on the rider, `CObjCART::GetParent()` — the queued event is keyed to the cart index), the pop is deferred so the real hit frame presents the death. Deferral is bounded by `kStaleLethalSwingHardCapMs` (6000 ms) so a swing whose consumer never fires still resolves; as soon as the swing state stops matching (interrupt, new swing, attacker death/despawn), the original 1.5 s grace applies again immediately. The avatar's pending-death backstop (above) now shares this rule and this cap, through `CombatPresentationQueue::has_live_lethal_pending()` and the orphan sweep's `fnPresentationStillLive` predicate (which, unlike `fnSwingStillPending`, also treats any `ProjectileImpact` event as live while its attacker exists). If projectile creation/impact is explicitly discarded, `DiscardQueuedCombatDamageFromAttacker()` presents lethal remote defender deaths, but still silently discards nonlethal projectile damage and keeps avatar pending-death behavior unchanged.

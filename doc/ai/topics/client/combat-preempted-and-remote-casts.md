- **Self-pre-empted swings are presented, not discarded (2026-09-14).** The discard above is for a *defender-caused* interrupt. When the interrupt is the **attacker's own next command** — a skill cast arriving while it still owes a hit frame — the server applied that swing at frame 0 and the honest rendering is to show it. `CObjAI::SetCMD_Skill2SELF/2OBJ/2POS` (client, after the `CanApplyCommand()` early-out, so a queued command that re-enters on `Execute` is covered) call `PresentPreemptedCombatSwing()`, which resolves the exact pending event and presents it through `PresentQueuedCombatDamageEvent()` → `ApplyPresentedCombatDamage()` (digit, HP, feedback, death). Same eligibility as the cancel path (a spawned projectile keeps its impact consumer) but deliberately **not** gated on `CS_BIT_ATTACK`: when the skill packet lands in the same frame as the `CombatSwing`, the attack motion never starts at all (`ProcCMD_ATTACK` never runs `Start_ATTACK`), and the hit is owed regardless. **Timing is decided by `m_bAttackSTART` on the motion object:** if no attack motion is attached, present at once; if one is running, the skill command only puts it in `CS_NEXT_STOP`, so its hit frame may still come — the first in-game test showed exactly that (hit frame at 0.42 s, fired right after the command into an empty queue, logged as `queued presentation miss`). So the hook then sets `m_bPreemptedSwingAwaitingMotionEnd` and leaves the event queued; either the hit frame presents it normally, or `Attack_END` (called from `Set_MOTION`'s prologue the instant a non-attack motion replaces it) presents it via the same function. Log signature for the deferred case: `pre-empted swing left to running attack motion` → `queued presentation pop` or `pre-empted swing presented ... reason attack motion replaced`. The local avatar and its mount are excluded (their skill flow starts at click time). Repro was Fearsome Terrasaurus King, whose when-damaged AI casts right after swinging: two 500-600 HP swings were discarded back to back and the killing blow presented death from a bar 1068 HP too high (`death correction deferred ... visible hp 1323 authoritative hp 255`). Log signature after the fix: `CombatTrace pre-empted swing presented` instead of `discarded without presentation ... reason swing motion cancelled`. The 3 s `Proc()` sweep is unchanged and still the tell for a motion lost some other way (MOVE/STOP repositioning, which the backlog self-corrects).
- **A remote caster's skill command is held behind the swing it would cut (2026-09-14).** Presenting the owed hit at pre-emption was honest but animation-less. The server itself sequences a cast after its own attack motion ends (its `SetCMD_Skill2OBJ` goes to `CS_NEXT_STOP`); only the packet is sent early. So `CObjAI::SetCMD_Skill2SELF/2OBJ/2POS` now push the command onto `m_CommandQueue` while `OwesConfirmedSwingHitFrame()` holds — pending swing set, projectile not spawned, defender still holding the event, and under `kOwedSwingHoldMs` (3 s, the orphan-sweep grace) — and `ProcQueuedCommand` will not pop it while that holds. The attack motion then starts/finishes normally, the hit frame presents the swing with its animation, and the cast pops right after. Bounds: the hold releases when the defender drops the event (its own sweep, death, despawn) or at 3 s, after which the present-on-pre-emption path applies; the attacker-side sweep waits on the queue being empty, so the time cap is what keeps the two from deadlocking. Skill commands only — move/stop are never held, so chase/repositioning are untouched, and each monster holds only its own cast. **The queue was written for the avatar's click-time flow, and three of its rules had to be re-stated for a remote caster** (each found in a boss session, 2026-09-14): (1) **valid at push** (`SetValid(true)`): `PopCommand` deletes an unvalidated skill command, and `GSV_SKILL_START` can arrive *after* the owed swing has popped the queue — a held Fireball was popped and deleted a second before its start packet, never played, and its damage was consumed by the next melee hit frame (`pop_for_attacker` is kind-agnostic and `Hitted()` cannot tell a melee frame from an impact — nobody passes `bIsBulletHit`; pre-existing, left alone). (2) **Newest wins — never keep two skill commands queued.** `PushCommand` erases older result-less skill commands, and that is the wanted behaviour (the server's `SetCMD_Skill2OBJ` is single-valued, so a newer cast supersedes the previous one); marking them "result received" to keep both deadlocked the monster: a popped command re-queues itself while the queue is non-empty (`CanApplyCommand`), so a Charge and a Fireball superseded within the same second reshuffled forever and neither started. (3) **Start permission is counted per queued command.** `m_bCanStartSkill` is one flag per object and the *current* cast's action clears it (`ProcSkillAction` → `SetStartSkill(false)`), so a `SKILL_START` that arrived for the queued cast was eaten — the popped Fireball waited in `CS_STOP` for a start it had already received and the avatar died by the 6 s timeout. `Recv_gsv_SKILL_START` now counts it (`OnRemoteSkillStartWhileQueued`, reset when a new command is pushed) and `ProcQueuedCommand` grants the flag when it executes the queued skill command. A cast the server cancels before its `Casting_START` (a Faint on the caster) gets no start and waits until the next server command re-syncs the monster. Also, a legacy `GSV_DAMAGE_OF_SKILL` whose skill is still *queued* on a remote caster (`HasSkillCommand`) now defers to that cast's action frame like a running cast's does — it used to present immediately, a second before the animation. **`Recv_gsv_RESULT_OF_SKILL` needs the same rule** (2026-09-15): the server sends the result right after the damage payload, and that handler drains every parked payload whenever the caster has no active/pending skill — which a held cast is not, so the just-parked hit was presented at once anyway. Found on the Sikuku Jailer's 3590: in ten casts, the eight whose held command had already run before the packets parked correctly; the two where the packets beat the command (the attack motion still finishing after the owed hit frame, `CS_BIT_INT` keeping `ProcQueuedCommand` from running) landed a 400-digit a second before any motion. The tell in a log: `skill command held` → `GSV_DAMAGE_OF_SKILL` → `skill damage queued` two lines later → `SetCMD_Skill2OBJ[...]` *after* it; a parked cast shows the queue line a second or more after the payload. The avatar is excluded from all of it. Log: `skill command held for owed swing` → `queued presentation pop` → `SetCMD_Skill2OBJ[...]`; a hold with no `SetCMD_Skill2OBJ[...]` for that caster afterwards is either a server-side supersede/cancel (no damage packet ever comes) or a regression here.
- **Remote-cast watchdog (2026-09-14).** A monster's applied cast waits in `ProcCMD_Skill2OBJECT` for `GSV_SKILL_START` (`bCanStartSkill()`), silently, in `CS_STOP`. If that start never comes — the server cancelled or superseded the cast, or the start was consumed by something else — the monster sat in `CMD_SKILL2OBJ` for good and a lethal `ProjectileImpact` event it had queued on the avatar could only die by the 6 s hard cap (`presented (pending death timeout) ... attacker 0`, the "alive client-side, dead server-side, boss idle" moment). `m_dwRemoteCastWaitSince` (on `CObjAI`) now stamps the first wait (`remote cast waiting for skill start`) and after `kRemoteCastStartWaitMs` (3 s) abandons it: `remote cast abandoned, no skill start after N ms`, `Casting_END`, `CMD_STOP`, and `DiscardQueuedProjectileDamageFromAttacker()` releases that caster's projectile events on the target — a remote defender's lethal one presents, the avatar's lowers the shadow and leaves the death to the ordinary 1.5 s backstop (`has_live_lethal_pending` is false once the event is gone). Melee events are untouched (`discard_for_attacker_kind`). Also `Do_SKILL` returning 0 for a remote caster now sets `CMD_STOP` (`remote cast ended without action`) as the server does, instead of parking it. The avatar is excluded from both. **This is instrumentation as much as a fix**: the one occurrence so far (16:35:50, cast applied one second after the avatar's lethal fireball event was queued, no impact ever) could not be attributed from the log; the next occurrence will say which branch it sat in.
- **A remote caster's queued skill command must be validated by `GSV_SKILL_START` (2026-09-14).** `CObjCHAR::Proc` returns early while an interruptible motion (casting `CS_CASTING`, skill action `CS_NEXT_STOP2`) is still playing, so a skill command that arrives mid-cast goes to `m_CommandQueue` and pops only after the current action motion ends — that is the right vehicle and it protects the previous cast's projectile frame. But `PopCommand` deletes any queued skill command whose `m_bValid` was never set, and the only setter is `Recv_gsv_SKILL_START`, whose handshake assumes the avatar's flow: "start flag already true → validate the queued command, else arm the flag for the direct command". A monster's start flag is cleared when its previous action motion begins (`ProcSkillAction` → `SetStartSkill(false)`), so the second cast's start was misread, the queued command was deleted, the cast never played, no projectile spawned, and its already-applied lethal `ProjectileImpact` event sat queued until the 6 s hard cap presented the death with no digit (`presented (pending death timeout) ... attacker 0`) while the server-side boss, its target dead, stood still. For any object other than the avatar with a non-empty queue, the handler now calls `SetValidFlag()` **and** `SetStartSkill(true)` (the popped command still has to pass `ProcCMD_Skill2OBJECT`'s `bCanStartSkill()` gate). Repro was Terrasaurus King casting Fireball twice 3 s apart.
- **Hit reactions are gone — do not restore them.** The retail flinch (`Set_MOTION(GetANI_Hit())` / `Set_STATE(CS_HIT)` on `DMG_ACT_HITTED`, gated on `!CS_BIT_INT2`) was removed from **both** sides: client `ApplyPresentedCombatFeedback` and server `CObjCHAR::Apply_DAMAGE`. They must stay in agreement — a flinch on one side only desynchronises the attack cadence. Three measured reasons (`scripts/measure-flinch-timing.py` re-derives all of it): **(1) its mechanical effect ran backwards** — damage is applied at **frame 0** of the attack motion (`CObjAI::Start_ATTACK` → `Set_MOTION(GetANI_Attack())` → `Attack_START` → `Apply_DAMAGE` + `Send_combat_swing`), so a flinch never cancelled a hit, it swapped the *remainder* of the attack motion for the hit motion (shorter for 85% of monsters, and never attack-speed-scaled since `Set_MOTION` defaults `fAniSpeed = 1.0f`), after which the attack restarted and dealt damage again — staggering a monster made it damage you **sooner**, up to 1.85x in a party; **(2) it was one-way** — players staggered monsters on 29–65% of hits, monsters staggered players on 0–12%, because monster ATK sits at parity with player DEF so the `(ATK+20)/(DEF+5)` term never cleared the gate; **(3) it was illegible** — the trigger is a hidden crit-adjacent roll (`iHitActRATE = (28 - iCriSuc) * (ATK+20)/(DEF+5) >= 10`; note `(28 - iCriSuc)` goes **negative** past 28, so it was never "always on"). Removing it is a −7% (solo, low level) to −46% (party of 4 at 240) monster-damage change. `CCal::Get_*DAMAGE` still sets `DMG_BIT_HITTED` and it still rides the wire; **nothing consumes it now**. Everything else about being hit is unchanged: digit, hit effect, hit sound and `StartVibration()` all still fire from `Hitted()`.
- **`HasUnconsumedConfirmedSwing()` / `ResolveOwedHitReaction()` / `m_bOwedHitReaction` are deliberately dormant.** They were the guard that let a flinch wait for the swing it interrupted, and are kept because they are the correct pattern for *any* future effect that cancels an attack motion (knockback, stun, a crit-only flinch): the server has already applied and sent that swing's damage, so the motion must reach its hit frame first, and the interrupt is then played by `ClearPendingCombatSwingPresentation()`. Nothing sets the flag today, so `ResolveOwedHitReaction()` is a no-op on every call. Projectile swings are excluded from the guard — the bullet owns their timing, not the motion.
